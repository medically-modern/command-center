### 5.55 The Supabase mirror — Profile Send Off, every column and every automation (Sep 2026)
Josh, 2026-09-29: *"we need to take this monday board and begin porting it into supabase.
eventually we want to be off monday completely and use only supabase. break down all of the
columns and automations ONLY ON THE PROFILE SEND OFF BOARD. were just starting with trying to
import that and have it MIRRORED so someday we can easily flip the switch but for right now it
should be sandboxed."*

**What shipped:** a read-only mirror. `services/supabase-mirror` copies the board — its shape,
every item, every cell, and every change it observes — into a `monday_mirror` schema in a
Supabase Postgres, and nothing in the Command Center reads it yet. **The mirror never writes to
monday** (`noMondayWrites.test.mjs` scans the service for the word `mutation`) and is **off
unless `MIRROR_ENABLED=1`**. Below: the design, the column inventory (164 columns, who writes
each), the automation inventory (35, with what each would become), and the flip plan.

⚠️ **Not done, on purpose:** no Supabase project is wired up from this repo (no URL, no key —
the service takes them as env vars on Railway), the app has no read path onto the mirror, and
no automation is ported. Each of those is a decision listed under *The flip* at the end.

#### 1. The mirror

**Where things live**
- `services/supabase-mirror/` — the Railway-shaped service (same skeleton as `baseline-cron`):
  `index.mjs` (the loop), `mirrorRules.mjs` (pure: what to ask monday, how an answer becomes
  rows — every rule tested without a network), `db/` (the schema, applied on every boot).
- `supabase/migrations/` — byte-identical copies of `db/*.sql` for `supabase db push`;
  `schemaAgreement.test.mjs` fails when the two drift, or when a generated file is not what its
  generator produces from the committed snapshot.
- `supabase/snapshots/` — the board's shape (`profile_send_off_board.json`: groups, columns,
  labels, column descriptions — **no item data**) and the automation inventory
  (`profile_send_off_automations.json`). Both PHI-free; both are the inputs to the generators.
- `scripts/supabase-mirror/` — `gen-view.mjs` (the typed view), `gen-seed.mjs` (the automations
  seed), `automations-from-mcp-dump.mjs` (the inventory from the monday MCP `list_automations`
  answer — ⚠️ **board automations are not in monday's public API**; the MCP tool is the only
  machine read, and it is how this inventory was taken).

**The schema (`db/0001_monday_mirror.sql`)** — `monday_mirror.boards · groups · columns · labels`
(the shape, every pass) · `items` (one row per item; `column_values` JSONB holds every cell's
`text` and parsed `value` exactly as monday returned them) · `item_changes` (one row per column
that differed between two reads, plus `__name__` / `__group__` / `__state__`) · `sync_runs` ·
`automations` (the inventory, with `port_status` / `port_target` / `port_notes` for the port).
Cell readers (`cv_text`, `cv_status_id`, `cv_date`, `cv_number`, `cv_phone`, `cv_email`,
`cv_address`/`cv_lat`/`cv_lng`, `cv_dropdown_ids`, `cv_files`, `cv_changed_at`) are IMMUTABLE
SQL functions, so the view can be indexed later.
- ⚠️ **RLS is on for every table with NO policies.** Through Supabase's API roles (`anon`,
  `authenticated`) the schema reads as empty; only the service role sees it. That is the sandbox.
  Don't add a policy until the app's read path is designed (§5 below).
- ⚠️ **`item_changes` is the history monday cannot show.** The board's activity log can't show the
  app's writes (CLAUDE.md §9); the mirror diffs every read against its copy, so a status flip the
  gateway made at 2:11 PM is a row here. `monday_updated_at` on the row is the closest a poll can
  come to "when"; `observed_at` is when the mirror saw it.

**The typed view (`db/0002_profile_send_off_view.sql`, GENERATED)** —
`monday_mirror.profile_send_off`: one Postgres column per board column, **named after the app's
own `COL` keys** (`lib/profile/mondayApi.ts`: `dupCheckResult` → `dup_check_result`), a board
column the app never mapped named from its title. Status → `<name>` (label) + `<name>_id` (label
id); dropdown → `<name>` + `<name>_ids INT[]`; date → DATE + `_time`; numbers → NUMERIC; phone /
email → the number / address; location → text + `_lat` / `_lng`; file → the files JSONB. 258
columns today. ⚠️ Regenerate, never hand-edit, and ship a change as a new migration — a view
cannot drop or reorder columns in place, so the file is `DROP VIEW` + `CREATE`.

**A pass (`syncBoard`)**
1. **shape** — groups, columns with `settings_str`, labels. Every pass (5,265 complexity, measured).
2. **full** — every item, every column, only when the board has never been fully read (or
   `MIRROR_FULL=1`). Pages of 50 with 400 ms between them: measured 203 complexity per item at
   164 columns, so ~10k a page, ~60 pages, ~570k for the board, once.
3. **incremental** — otherwise: items ordered `__last_updated__ desc` (⚠️ the only ordering monday
   honours for this; its `greater_than` filter on `__last_updated__` returns nothing — measured),
   read until the page crosses the previous pass's watermark minus a 5-minute overlap. A quiet
   pass is one ~200-complexity request.
4. **reconcile** — daily: an ids-only scan of the whole board (2,020 per 100 items). Items monday
   stopped listing become `state = 'missing'` (⚠️ monday does not say deleted vs archived, so the
   mirror doesn't claim either); an item whose group or `updated_at` disagrees with the copy —
   a move that did not touch `updated_at` — is re-read by id.
- Every item read is hashed (name + group + every cell); an unchanged item touches `last_seen_at`
  and nothing else. Every answer's `complexity.after` is honoured: under
  `MIRROR_COMPLEXITY_FLOOR` (2M) the loop sleeps out the minute (CLAUDE.md §9's August incident).
- Verified end to end against a real Postgres 16 with a fake monday (`syncBoard.test.mjs`: schema
  applies, full read lands items and labels, incremental records the diff, reconcile marks the
  vanished item and re-reads the silent move, the view reads labels/dates/numbers/phones/dropdowns
  back, and every request sent was a query). `labelsOf` was checked against the live
  `settings_str` of all 72 status/dropdown columns: 0 mismatches with the snapshot. Both GraphQL
  shapes were run against the live board through the monday MCP read tool.
- ⚠️ **What the mirror does NOT carry:** item *updates* (the comment thread), file bytes (only
  the files' metadata; a URL is signed on request, §5.30f), the activity log, board views and
  forms, subitems (this board has none). Add `updates` to the item query if the port needs them.

**Running it** — Railway service from `services/supabase-mirror` (Dockerfile). Env:
`MIRROR_ENABLED=1`, `MONDAY_API_TOKEN` (read scope), `SUPABASE_DB_URL` (the project's **Session
pooler** or direct connection string, `sslmode=require` — ⚠️ not the transaction pooler on 6543,
which refuses `pg`'s prepared statements), `MIRROR_BOARD_IDS` (default `18406352652`). `DRY_RUN=1`
reads monday and writes nothing; `ONCE=1` runs one pass. Full list in the service README.

**Connecting Claude Code (2026-09-29)** — `.mcp.json` at the repo root registers Supabase's hosted
MCP server for project `xjwbfkvhqmztvblfyyia`; it needs a one-time browser OAuth sign-in (`/mcp` →
`supabase` → *Authenticate*) in a local session, after which the MCP's `apply_migration` tool applies
the three migrations in order and `execute_sql` reads the mirror back. A cloud session cannot
complete the OAuth step (measured: the endpoint answers 401 with `authorization_servers:
api.supabase.com`, authorization-code grant only), so from there the schema and the first pass need
`SUPABASE_DB_URL` as an environment secret. The two Supabase agent skills live under
`.claude/skills/` (`skills-lock.json` pins them). On Railway the service goes in project
`handsome-simplicity` next to `cmd ctr server`, sharing its `MONDAY_API_TOKEN` as a reference
variable; not deployed yet (Josh's call, and it needs the Supabase connection string).

#### 5. The flip — what "easily flip the switch" needs, in order

Nothing below is built. Each is a decision for Josh; the mirror is what makes them possible.

1. **Turn the mirror on** (Railway service + a Supabase project; the three env vars). Watch
   `sync_runs` for a day: a full pass, then incremental passes of one request. Compare
   `select group_id, count(*) from monday_mirror.items where state='active' group by 1` with the
   board's group counts and the role bars (§5.8). This is the point of the sandbox: the copy is
   proven faithful before anything reads it.
2. **Decide the write path.** Today four things write this board besides the app (form backend,
   Stedi, the duplicate check, the fax intake) and 16 webhooks fan changes out to more. A flip
   is not "the app reads Supabase"; it is every writer moving, or a reverse sync keeping monday
   current for the ones that haven't. Order that works: (a) the app reads the view behind a flag
   and logs where it disagrees with monday; (b) the app writes Supabase FIRST and a reverse sync
   writes monday (so the other services keep working unchanged); (c) services re-point one at a
   time, each with its webhook replaced by a Supabase one; (d) the two stage hops become inserts
   into the next mirrored board; (e) monday goes read-only, then off.
3. **The counting contract moves with it** (§5.8): the sidebar, `useRoleCounts`, both baseline
   generators and Oversight's `CHART_FILTERS` all encode the same group + status rules; a Supabase
   read path re-implements them once, as SQL, and the four keep-in-agreement lists collapse.
4. **Things monday gave for free that Postgres has to grow:** label ids (keep them — the view
   carries both id and label), the activity log (`item_changes` replaces it), item updates and
   file bytes (not mirrored today), and the automations above.

**Keep-in-agreement:** `db/*.sql` ⇄ `supabase/migrations/*.sql` ⇄ the generators ⇄ the snapshots
(`schemaAgreement.test.mjs`) · `COL` in `lib/profile/mondayApi.ts` ⇄ the board snapshot (every
mapped id must exist on the board — same test) · the automation inventory ⇄ the board (re-run the
MCP `list_automations` dump and `automations-from-mcp-dump.mjs` after any board change).

**Tests:** `services/supabase-mirror/mirrorRules.test.mjs`, `noMondayWrites.test.mjs`,
`schemaAgreement.test.mjs`, `syncBoard.test.mjs` (needs `MIRROR_TEST_DB_URL`).
