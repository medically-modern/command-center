### 5.47b Voicemail is archived too — the tighter clock (Sep 2026)
Josh, 2026-09-23: *"do the voicemail archive"* — §5.47's phase 5, and the half with less time on
it. Built: `services/monday-gateway/voicemailArchive.mjs` + `voicemailArchiveRules.mjs` (pure,
tested), into the **same `call-recordings` bucket** under a `voicemails/` prefix, with the index on
the messaging Postgres. **No board change; gateway only.**

⚠️⚠️ **VOICEMAIL IS NOT IN THE RECORDING SYSTEM AT ALL, AND ITS CLOCK IS THREE TIMES TIGHTER.** A
voicemail is a **message-store** record, so it lives on the ~30-day window §5.27 measured (oldest
surviving record 2026-08-01; every earlier `dateTo` returns 0 rows for EVERY number), not on the
90-day recording cliff. And the failure is QUIETER than the recordings one: a purged recording at
least leaves its call-log row behind, so the call is still visible with no audio — a purged
voicemail leaves **nothing**, so *"this patient never left a message"* and *"this patient left a
message we no longer have"* become the same answer, with nothing anywhere saying which.

**Same shape as §5.47, for the same reasons**, and the ones that are load-bearing are pinned by
`voicemailArchiveRules.test.mjs` (58 tests; **nine protections each verified to fail when
removed**): metadata first / audio second · **oldest-first** drain (the oldest unarchived
message is the one closest to deletion) · **the scan may only ever move `none` → `pending`** · the
object is written **before** the row is marked stored · a **200 is not audio** · a **429 never
burns an attempt** · every presigned URL audited · the health route survives the kill switch · the
forced run is authenticated **and** rate-floored · the presign self-check is a ranged **GET**,
never a HEAD.

⚠️ **ONE WINDOW, NOT TWO — and that is earned by a measurement, not a corner cut.**
`callArchiveRules` splits `SCAN_DAYS` from `WINDOW_DAYS` because the call log is ~111 rows a
business day, so a 95-day repair pass is ~16 pages. Voicemail is ~**2.6 a day** (78 in 30 days,
§5.13b), so a 35-day window is under a hundred records — **one page**. Every run therefore reads
the WHOLE window and every run is a repair pass, which removes the deep/shallow bookkeeping and
the "was the deep pass complete" verdict with it. Revisit only if volume grows two orders of
magnitude.

⚠️⚠️ **`messageType=VoiceMail` IS A SINGLE VALUE, and that is the difference from `smsArchive`,
which passes no type at all.** The MULTI-value syntax 400s on this account (§5.5 — it broke the
whole thread load when it was tried), which is why that module filters in code; ONE value is
proven in production by the SPA's `fetchVoicemails`, and filtering server-side is what turns a
~5,000-record window into ~90. ⚠️ **No `direction` filter**, deliberately: an archive must not
silently exclude a category, and the rare outbound row costs nothing when the window is one page.
⚠️ `dateFrom` is explicit — this API defaults to roughly the last 24 hours, so an omitted bound
quietly turns a 35-day pass into a one-day one.

⚠️⚠️ **THE TWO ARCHIVES PARTITION THE MESSAGE STORE — `smsArchiveRules.isArchivable` still
refuses VoiceMail by name**, with its own comment that archiving one as a text *"would be worse
than the gap it fills"*. That exclusion is what makes this module necessary rather than duplicative,
so a test pins it: if somebody ever "fixes" it, the build fails and says why.

⚠️ **The audio part is NEVER `attachments[0]`.** A voicemail carries the audio AND — where the
account produces one — a `text/plain` transcript, in an order RingCentral does not promise. Taking
the first would store a transcript under an `.mp3` key: a file that will not play, with nothing
saying why. `audioAttachment` matches the content type first and `type === "AudioRecording"` as the
fallback, exactly as `fetchVoicemails` does, so the archive and the live list cannot disagree about
which part is the message.

⚠️⚠️ **TRANSCRIPTS ARE FETCHED, AND THEIR ABSENCE IS THE EXPECTED READING.** §5.28 records that
transcription is a per-account feature and it is **not established** that it is on here; when it is
off, `vmTranscriptionStatus` is `NotAvailable`, there is no text attachment, and `drainTranscriptQueue`
does nothing at all. **Nothing may mark a row failed for want of a transcript** (a test scans that
function for `audio_state` and `audioFailed` and fails if either appears), and `archiveHealth`
reports the count while never treating zero as a defect — zero is the expected reading, and it is
reported so the OTHER explanation (the fetch is broken) is visible at all. ⚠️ It is its own pass
rather than part of the audio drain because transcription is **async**: a voicemail whose audio we
stored within the hour may not have a transcript for minutes, and `transcript_uri` is refreshed on
every scan so a late one is still picked up inside the window.

⚠️ **Six rules are RE-EXPORTED from `callArchiveRules`, never re-implemented** — `extensionFor`
(one names an object, the other names a download, and per-account MP3-vs-WAV is exactly what a
divergent copy gets wrong), `nextAudioState` (`gone` is terminal and nothing retries it, so two
readings of "is this really gone" is two chances to throw audio away), `isOfficeHours` (two
definitions is one of them wrong twice a year at the DST boundary), `last10`/`last4`/`windowStart`
(a read that normalised differently from the write matches nothing and reports an empty history).
A test asserts the exported functions are the SAME OBJECTS.

⚠️ **PHI, on §5.47's terms exactly**: the **messaging pool** (`ASSIGNMENTS_DATABASE_URL`), never
the audit pool — **do not move this table**, and `registerVoicemailArchive` is called from
`messaging.mjs` for that reason with a test pinning it — and **HMAC + last4, never the number**.
⚠️ **`from.name` is deliberately NOT stored**: it is caller ID, mostly carrier CNAM junk
("WIRELESS CALLER", "CELLCO PARTNERSHIP", §5.28) and occasionally a real patient's name, i.e. a
name in the clear for no benefit when the number's HMAC already joins to `patient_directory`.
⚠️ The **transcript** is a patient's spoken words as text — the same category as `sms_archive`'s
message bodies, bounded the same two ways. ⚠️ **Keep-forever**, matching §5.47: no prune job and
no retention variable, and that is the decision rather than an oversight.

⚠️ **The SAME bucket and the SAME credentials as the recordings.** `callArchiveStore.mjs` is a
generic S3 wrapper named for its first caller; a second store module would mean five more Railway
variables that must be set before this does anything, and a half-configured second store is a new
silent failure mode for no benefit. They are kept apart by the object-key **prefix**
(`voicemails/` vs `recordings/`), which a test pins. **So this needs NO new Railway variable to
work** — every `VOICEMAIL_ARCHIVE_*` var is an optional tuning knob, plus the
`VOICEMAIL_ARCHIVE_ENABLED=0` kill switch.

**Routes:** `GET /voicemail/archive-health` (**unauthenticated**, counts and timestamps only — same
posture as `/calls/archive-health`) · `POST /voicemail/archive-run` (authenticated
**and** rate-floored) · `GET /voicemail/audio?messageId=` (302 to a presigned URL, `?mode=proxy` to
stream through the gateway, every issuance written to `voicemail_archive_access`) · `POST
/voicemail/archive/query`. Auth is a Google employee **or** the SAME `CALL_ARCHIVE_SERVICE_TOKEN` —
both routes answer the one question *"may this service read archived patient media"*, so a second
token would be a second secret to rotate for no additional boundary.
⚠️ **The query route is deliberately ALSO the batched "do we hold audio for these"**, rather than a
second `/voicemail/have` beside it: pass `messageIds` and it answers for exactly those. One route
doing both beats shipping an endpoint with no caller (§5.31b — *"a module nobody calls does not
fail; it is absent, and its green tests say otherwise"*). ⚠️ An explicit id list is **not**
date-bounded: a caller asking about specific voicemails already knows which it wants, and silently
dropping the ones older than `sinceDays` would answer "we hold no audio for that" about a message
sitting in the bucket — the exact wrong answer for the aged-out messages this exists for.

**Watched by `services/calls-monitor`** via `VOICEMAIL_ARCHIVE_HEALTH_URL`, through the **same
`archiveFaults`** the recordings use — one rule, two labels, because they have the same failure
modes and the same "a backlog is not a fault" discipline, and a second copy would be two chances to
page for a working system. ⚠️ **A separate push from the recordings one**: different remedies,
different urgencies, and a single notification carrying both is one somebody reads as whichever
half they recognise. ⚠️ The missing-bucket message still names the **`CALL_ARCHIVE_*`** variables
even under the voicemail label, because that really is the remedy — saying anything else would send
somebody looking for variables that do not exist.

⚠️⚠️ **STALENESS IS MEASURED ON THE LAST *COMPLETE* PASS, NOT THE LAST `ok` ONE — and that one
rule is what lets this file drop the call archive's deep/shallow bookkeeping honestly.** A run cut
short by the rate limiter is still recorded `ok` (it did what it could, and losing that signal
would be worse) but it did NOT read the window, so measuring on `ok` alone would let an archive
that sheds **every single pass** report healthy forever while the 30-day window closes on
everything in it. The health query therefore asks for `ok AND NOT truncated AND NOT shed`. One shed
run is routine and trips nothing; six hours of them is a fault. ⚠️ It is also **not ok when no run
has ever completed a pass**, however many rows the table holds — a job deployed but never actually
working cannot report healthy — and the two cases say different sentences, because "it has never
run" and "it runs and is always cut short" have different remedies.

⚠️ **The boot run is offset** (150s, against the call archive's 90s) so a redeploy does not fire two
full scans at the same RingCentral account in the same second.

⚠️ **Every SQL string in `voicemailArchive.mjs` is a JS template literal, so no backticks may
appear inside one — comments included.** `callArchive.mjs`'s SCHEMA carries the same warning;
this file earned it again the same day, on a comment quoting a SQL clause.

⚠️ **Starting this recovers nothing.** Everything older than ~30 days was already gone when it was
written, and every day it is not running is ~2.6 more patient messages purged.

**Keep-in-agreement:**
1. `voicemailArchiveRules.WINDOW_DAYS` ⇄ RingCentral's real message-store retention ⇄
   `STALE_AFTER_MS` ⇄ `calls-monitor`'s `archiveFaults`. **A window shorter than retention loses
   voicemail silently, with no surviving row to notice.**
2. The six re-exports from `callArchiveRules` — never re-implement one here
   (`voicemailArchiveRules.test.mjs` scans for a local definition of each).
3. `smsArchiveRules.isArchivable` must keep refusing `VoiceMail`, or the two archives overlap.
4. `audioAttachment` ⇄ `src/lib/fax/ringcentralApi.ts` `fetchVoicemails` — one reading of the same
   payload, so the archive and the live list cannot disagree about which part is the message.
5. `AUDIO_GAP_MS` ⇄ whatever group `X-Rate-Limit-Group` actually reports for message-store content
   (`noteRateLimitGroup` logs it once per path shape on the first live run). It is set to the
   call archive's HEAVY pace because being slower than necessary costs nothing at ~90 records a
   window, and being faster than the real ceiling costs 429s on the line that carries patient texting.
6. `registerVoicemailArchive` is called from **`messaging.mjs`**, never `index.mjs`, so it lands on
   the messaging pool (pinned by a test).
