### 5.57 Remove from Stuck — a manager's undo, on the patient screen (Oct 2026)
Brandon, 2026-10-01: *"let's add a Remove from Stuck button to the patient profile page, which undo's
a stuck. But let's have a setting in users where we can assign only managers to have that button
available to them. It should go next to the stuck warning on top."* Josh, the same day: *"basically
automatically any one with manager privilege gets that button"* · *"with a notif that it sucessfully
sent to monday"*. **No board change; app only.**

**Where it is.** The patient screen's Onboarding view, in the snapshot header, directly beside the red
chip *"Stuck — out of the pipeline until a manager moves them back"*
(`components/patient/OnboardingView.tsx` → `components/patient/RemoveFromStuck.tsx`). The button only
OPENS a panel under that row; nothing is written until the manager confirms a stage there. On success:
a toast *"<name> removed from Stuck — Saved to Monday — back in <group>."*, a stamped note on the
record (`[ts] <Stage>: Removed from Stuck — back to <Stage>. —XX`, through the Comms Hub's own
`appendNoteToRecord`), and the screen re-reads.

**Who.** ⚠️ **Managers only, read off the SIGNED-IN person** (`useAccessContext().access.type`),
checked on the button and again inside the handler (§5.39g-h: write guards never read the borrow).
**There is no Users-page switch** — on Josh's word the Manager tick on `/access` IS the setting, so
it is not an `ABILITIES` entry. A processor sees the chip and no button; the chip already says a
manager moves them back.

**Which boards.** Every board the app can mark Stuck: Welcome Call, Medical Evaluation, Insurance,
Profile Send Off (`lib/oversight/removeFromStuck.ts` `STUCK_PLANS`). DTC Intake has Stuck groups but
is read-only here (§3), so it has no plan and no button. A COMPLETED record never gets it.

⚠️⚠️ **"BACK" IS WHERE MONDAY'S ACTIVITY LOG SAYS, NEVER A GUESS.** Stuck is a group (§5.18) and
nothing on the item remembers the group it left. The item's activity log does:
`move_pulse_from_group` carries `source_group` → `dest_group` (the Stuck group), and on the three
boards whose Stuck is an advancer label, the `update_column_value` into it carries `previous_value`.
`readStuckOrigin` reads up to five pages of 100, newest first, ONCE when the panel opens.
- **Welcome Call / Profile Send Off decide by the GROUP** — their queues read the group.
- **Medical Evaluation / Insurance decide by the ADVANCER** — every ME step shares the one
  "2. Medical Necessity" group, and an Insurance DVS item lingers in whichever group an automation
  last left it. A Medical Evaluation move with no advancer change is therefore NOT matched.
- **No answer → nothing preselected**, and the confirm stays disabled until the manager picks. This
  is the ordinary case for the oldest rows: the 2026-04-29 import put items straight into Stuck, so
  their log has no move (measured on Welcome Call's Joseph Boyle row).
- Measured on live items 2026-10-01 (parser run in memory, nothing logged): Welcome Call (John
  Larkin) → Welcome Call, advancer 7 → cleared; Medical Evaluation → Chase Clinicals (11);
  Insurance → Benefits / SoS (3); Profile Send Off → New Form — Partial Leads.

**What each board's press writes — checked against `list_automations` on all four boards, label ids
read off `settings_str`, 2026-10-01.** Group move FIRST, then at most one Stage Advancer write, then
a read-back; the success toast only fires once Monday reads the patient out of Stuck.

Each "what else" is shown to the manager as the step's caveat before the press. Every advancer change
on these boards also fires the "column changed → webhook" recipes (e.g. 581302892 on Welcome Call),
as every advancer write in the app already does.

⚠️⚠️ **WELCOME CALL NEVER WRITES "Welcome Call" (7) BACK.** A change to 7 runs seven "set Autotext
Type" workflows (7918358649, 7918358790, 7918358802, 7920267147, 7920267171, 7920267211,
7920267249), and Autotext Type changing is what fires the board's welcome texts (573200740 …
603174271, *"YOUR CGM IS APPROVED AND READY FOR SHIPMENT …"*). Writing 7 back could text the patient
a second time. The Welcome Call queue reads the GROUP, so the advancer is cleared instead; the rep's
Send writes "Review Profile" from blank exactly as from 7. It is cleared ONLY while it still says
"Stuck / Don't Proceed": a row dragged into Stuck by hand kept its "Welcome Call", and that is left.
Pinned by `removeFromStuck.test.ts`.
⚠️ **That clear is not §9's forbidden "repair a stuck patient by clearing the advancer".** That rule
is about an advancer that already FIRED (the downstream item exists, so the next press duplicates it).
"Stuck / Don't Proceed" creates nothing downstream — its one automation (7918322174) moves the item
to Stuck.
⚠️ **Profile Send Off's `stuck reason` column is NEVER written** — automation 7918293476 moves the
item INTO Stuck on any change to it, so clearing the old reason would put the patient straight back.
⚠️ **The Escalation column is not touched.** Approving the Stuck already set it to Done (WC, ME) or
blank (Insurance), which is what lands the patient in the rep's queue; restoring the "Final
Escalation Required" they had before the approval would undo the manager's decision too.
⚠️ **Not an `executeWritesWithVerification` transaction**, for §5.34's reason: there are no data
columns for an automation to read, only a group move and one advancer write. The read-back is kept.
⚠️ **Group first, advancer second** so Insurance's Benefits routing (→ DVS → its own group move) runs
after our move and wins, as on an ordinary arrival. A failure between the two leaves a working-group
item whose advancer still says Stuck; `canRemoveFromStuck` reads group OR advancer, so the button is
still offered and a second press is safe (the move is a no-op, the advancer lands).

**The screen after.** `dossierApi.patchCachedPlacement` patches every cached copy of the record
(group, advancer, `isStuck`, `isCompleted`, `route`, re-derived by `toDossierItem`'s own rules), so
both hosts show it: `PatientPage`'s reload reads through the cache, and the Comms hub pane's
`useDossier.reload` only rebuilds from those objects. **Welcome Call's sub-step tabs fall back to the
GROUP when the advancer names no step** (`stagePanels.SUB_STAGE_BY_GROUP`): without it a patient put
back in Welcome Call with a cleared advancer opened on Final Confirm, the last tab an unrecognised
advancer "reaches" (which is also why a Stuck Welcome Call record opens on Final Confirm).

**Not changed, on purpose:** Date of Stage Start (the "N days here" chip keeps counting from the
original arrival); Follow Up / snooze (their pre-Stuck state); the stuck reason/notes already on the
record.

**Rendered before shipping** (throwaway harness, fake data, Monday stubbed — not committed) at 1440,
1100 and 390, light and dark: the button sits on the chip's row at every width, the panel wraps at
390 with no horizontal scroll, a processor sees no button, no-history leaves the confirm disabled,
success shows the toast and the record goes Live on the Welcome Call tab.
