### 5.56 Expedited — a manager's "work them the same day" mark (Sep 2026)
Brandon, 2026-09-30: *"Jsoh can we add a feature where katie has the ability to make a patient
'Expedited'. What this should do, is the following: Instead of when going to a new board and making
the next action date the following date, it makes it the same date."* Josh's rulings the same day:
**managers only**, set **only on the intake stages** (Referral Intake, Info Collection, and Profile
Clean-Up), **same day for Auth Outstanding too**, and **leave Benefits alone**.

**Board change (2026-09-30):** a status column titled **Expedited**, with ONE label, `Expedited`,
on four boards. All four read back from `settings_str` after creation — the label is id **2**
everywhere. Constants: `lib/shared/expedited.ts`.

| Board | Column | Who fills it |
|---|---|---|
| Profile Send Off `18406352652` | `color_mm7pywyh` | the Command Center (the manager's tick) — the ONLY write |
| Medical Evaluation `18406060017` | `color_mm7pkb92` | hop **7917676280** (Advance to MN) |
| Insurance `18410601299` | `color_mm7ppqbn` | hop **7918295320** (MN → Insurance) |
| Welcome Call `18410804557` | `color_mm7p9hm0` | hops **7918324247** (Insurance → WC) and **7923595946** (cash pay, PSO → WC, §5.48) |

⚠️⚠️ **THE HOPS MUST MAP IT, AND THAT IS A PERSON IN MONDAY'S UI** (Josh took the four
mappings, 2026-09-30). Until a hop copies the column, every patient it creates reads blank = normal, so nothing
breaks — expedited patients just wait a day as before. Check by expediting a test patient and
reading the next board's column, never by reading the automation list alone. The hops copy a
status **by label text**, so the label must read exactly `Expedited` on all four boards.

⚠️ **A blank means NORMAL here** — the one column where §9's "a blank is unknown, not no" does not
bite. Unknown and normal lead to the same place (the next-business-day date every arrival already
gets), so a missing value can never sell or skip anything.

**What the mark changes — three stamps, one decision each (`isExpedited`):**
1. **Evaluate arrival** (`hooks/masheke/useMondayPatients`, §5.6b): blank Next Action Date →
   today instead of `addBusinessDaysIso(today, 1)`.
2. **Submit Auth → Auth Outstanding** (`lib/samantha/mondayWrite`, §5.32a): Follow Up Date → today.
   The task's declared `value` and its `fn` still write the same date (§5.2's fast path).
3. **Welcome Call arrival** (`hooks/welcomeCall/useMondayPatients`, §5.31i): blank Follow Up Date →
   today. This covers cash pay patients too, who reach Welcome Call straight from Profile Send Off.

**Benefits is untouched, by ruling.** It is already same-day: nothing dates a Benefits arrival —
checked in the code and in every automation on Medical Evaluation (32 + 16) and Insurance
(45 + 18) on 2026-09-30; none writes `color_mm34jz1x` / `date_mm34m2dz`. Brandon believed Benefits
was next-day; it is not. Welcome Call was ALREADY next-day (§5.31i, 2026-09-22), which his note
also asked for.
⚠️ **The §5.8 counting contract did not move.** All three stamps write BOARD values that the
sidebar, `useRoleCounts` and both baseline generators already read.

**The tick — `components/profile/ExpediteToggle`.**
- **Where:** at the foot of each intake stage's readiness list, straight above the button that
  hands the patient on. Referral Intake: `ProfilePage`'s *Ready to Send Off?* card, OUTSIDE the
  collapsible checklist (a manager must not have to open it to see it). Info Collection:
  `UnverifiedReferralsPage`'s *Ready to Advance?* card, under the gate. Profile Clean-Up: the
  right pane's *Ready to Send Off?*, above the advance to MN — and NOT also the left pane's copy
  (`!isCleanUp`), so one screen never shows two. Styled by `.xp-line` in
  `pages/profile/redesign.css` (the one file both pages load), amber rather than rose because
  rose on these pages means "missing".
- ⚠️ **The PATIENT's queue decides on `ProfilePage`, not the URL** — same rule as its exits
  (`!selectedInSystem`). An Already In System patient never gets the tick.
- ⚠️ **Managers only, from the SIGNED-IN person** (`useAccessContext().access.type === "manager"`),
  never a borrowed view (§5.39g-h). While `managers[]` is empty everyone is a manager (§5.3).
- **A processor sees nothing** on a normal patient, and a read-only checked line on an expedited
  one — so the rep knows why the next stage has them due today. A disabled empty box on every
  patient would be noise for a control they can never use; this is a manager's control, not an
  ability someone forgot to grant, so §5.39g-h's "show it inert with the reason" does not apply.

**How the tick writes — `lib/profile/expedite.ts`.**
- ⚠️ **At the press, straight to the board** (`writeExpedited`), not on Save or Advance: the
  manager who ticks is often not the rep who advances. It then reads the column back (up to 5 ×
  800ms). Confirmed → the `expedited` overlay key is dropped and the page refetches, so the tick
  does not light the "unsaved edits" marks for a change that is already saved. Not confirmed →
  the overlay stays (the screen shows what was asked) and a warning toast says so. A failed
  WRITE puts the old value back.
- ⚠️ **Every write is addressed to the item id captured at the press** (`onLocal(id, …)` is the
  hook's `updateLocal`, not the page's `edit`/`onUpdate`, which follow the selection) — a rep
  can switch patients mid-write.
- ⚠️ **The mark rides BOTH advance batches** (`expeditedAdvanceTask`): `sendPatientToMonday`
  (Referral Intake) and `buildAdvanceTasks` (Clean-Up → MN). The hop copies the column the instant
  Move to Onboarding flips, and Monday answers 200 before a value is indexed (§5.2), so a tick
  pressed a second before Advance is read back — exact match on the label — before the advancer
  may fire.
- ⚠️⚠️ **THE BATCH ONLY EVER WRITES THE MARK, NEVER A CLEAR.** A rep's screen can trail a
  manager's tick by one poll; a clear written from that stale copy would silently un-expedite the
  patient. Un-ticking is the manager's own immediate write and nothing else's.
- Info Collection → Clean-Up is the same board and item, so that advance carries nothing extra.

**Not done, on purpose:** no sidebar pill (the intake list is ~1,900 rows on a deliberately slim
read, §5.25 — adding a column there is a cost this didn't need); no stamped note naming who
expedited (Monday's activity log shows the gateway, not the person — add one if an audit trail is
wanted). **Not checked:** the Supabase mirror (§5.55) — its `0002` view and the 2026-09-29 board
snapshot predate this column.

**Keep-in-agreement:** `EXPEDITED_COL` ⇄ each board's `COL.expedited` ⇄ each board's read list
(`READ_COLUMN_IDS`, and Insurance's `AUTH_READ_COLUMN_IDS`) ⇄ each mapping — pinned by
`lib/shared/expedited.test.ts`, which also pins the two pages as the only mounts. The three stamps
are pinned by `arrivalDate.test.ts`, `authArrivalDate.test.ts` and `welcomeCallSnooze.test.ts`;
the writes and the batches by `lib/profile/expedite.test.ts`; the tick by
`ExpediteToggle.test.tsx`.
