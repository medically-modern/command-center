01

What this document is

This guide states only rules that are actually defined in the system — a named column, a named role, a specific comparison the code performs. Every rule block cites the file it comes from so you can have someone check it.

Where a behaviour is a judgement call rather than a defined rule, this guide says so explicitly instead of guessing. Where a number appears (30 seconds, 8 attempts, 95 seconds), it is read from the code, not estimated.

What it does not cover

  • How to do your job in each stage. This is about the machinery, not the clinical or insurance work.
  • Monday automations individually. They are configured on the boards, not in code, so they can't be read the same way. This guide tells you when to suspect one.
  • The Railway services' internals. They own certain columns; this guide names which, and stops there.
  • Auth Denied. That stage is under construction and deliberately has no manager views built for it.
A note on the engineering docs

The repository's CLAUDE.md is the engineering reference, and it is far more detailed than this. It can also fall behind the code: while preparing this guide, its description of the Patient Intake split was found to describe a rule that was changed on 10 August 2026. Where this guide and CLAUDE.md disagree, the rules stated here were read from the code on the date on the cover.

02

What the Command Center is

One paragraph that the rest of the document depends on.

The Command Center is a web app that reads and writes Monday.com columns. It has no patient database of its own — every patient fact you see on screen is a column on a Monday board, fetched moments ago. (It does keep two small things of its own: a cache of the role-bar numbers in your browser, and the list of who can see what, stored in a file in GitHub.)

Patients move between stages through Monday's own automations. Each board has a status column acting as the Stage Advancer; automations configured on the board watch it and move the item. The app writes the stage data first, confirms it landed, and writes the Stage Advancer last.

The refresh delay is real, and it is two different numbers

The patient lists on a role page refresh every 30 seconds. The numbers on the role bars refresh every 60 seconds. Neither is instant, and they are not in step with each other.

So a list and its own count can legitimately disagree for up to a minute after something changes. Before reporting a mismatch, reload and look again.

Defined in src/hooks/masheke/useMondayPatients.ts, src/hooks/samantha/useMondayPatients.ts (POLL_MS = 30_000) and src/hooks/useRoleCounts.ts (POLL_MS = 60_000).

03

The five owners

Every problem in this system belongs to one of five categories. Naming the category is most of the diagnosis, because it decides who can fix it.

Board data

A value in a column is wrong, missing, or was never set. Fixed on the board by anyone with access.

Board setup

A column, a status label, or an automation was renamed, deleted, or switched off. Fixed in Monday by a board admin. No code.

A bot

A Railway service owns those columns — eligibility, DVS, doctor lookup, texting. Backend work; the app cannot fix it.

The save

The app attempted a write and it did not land, or has not landed yet. Check what the toast said, then retry or escalate.

App rules

Which queue a patient lands in, whether they're counted, which chart shows them. Code change — and see section 07.

The fork every diagnosis starts at

Open the patient's item on the Monday board and read the columns themselves.

If the board is wrong, something wrote the wrong value or nothing wrote at all — that is Board data, Board setup, A bot, or The save. If the board is right and the screen disagrees, the data is fine and a rule is filtering or counting it — that is App rules. One look splits the problem in half.

04

How a patient reaches a queue

A patient must pass three gates in order to appear in somebody's work list. Nearly every “where did they go?” question is one of these three.

GATE 1Which queue — board, group, and for some stages a splitter column

Most stages are simply “this board, this group”. Three places split one group into more than one role:

  • Medical Evaluation is one group split by the Stage Advancer text, matched exactly: Evaluate MN, Send Request, Confirm Receipt, Chase Clinicals, Doctor Appointment.
  • Chase Clinicals splits again on Clinicals Method: Parachute or Email go to Chase — Email & Parachute; everything else, including blank, goes to Chase — Fax.
  • Profile Send Off separates Already In System = Yes into its own role. Everything else in the 1. Intake group is Verified Referrals.
Corrected — changed 10 August 2026

Patient Intake is no longer a split of the 1. Intake group. It is now the DTC form's own two groups on the same board, and nothing else. Referral Type and Referral Source no longer route anyone to it — they are still shown and still labelled in Oversight, but they no longer decide the queue.

If you have been told that a “Patient” referral type moves someone to Patient Intake, that is out of date.

Defined in src/lib/profile/referralSplit.ts and duplicated in src/hooks/useRoleCounts.ts.

GATE 2Due today — and there are three different rules

This is the most common source of confusion, because the rule is not the same on every board. There are three distinct shapes:

GATE 3Escalation removes the patient from the rep — with one exception

An escalated patient leaves the rep's list and the rep's count, and appears in a manager column in Pipeline Oversight. That is what escalating is for. There are two rungs:

  • Manager Escalation Required — the Manager Intervention column.
  • Final Escalation Required — the Final Decisions column. On the Medical Evaluation board this specifically means a rep has proposed that the patient be marked stuck; a manager approves or returns it. It is a proposal, not a decision.

On the Medical Evaluation board, a proposed-stuck patient is counted in neither the active count nor the escalated count. They are skipped entirely, and are reached through the manager views.

The exception

DVS ignores escalation. Escalated patients stay in the DVS queue and the DVS count, because the DVS queue keys off the DVS and claims status columns instead. An escalation label carried in from an earlier stage must not hide them.

Defined in src/hooks/useRoleCounts.ts. Escalation columns: Medical Evaluation color_mm1x7997, Insurance color_mm2vsh2f, Welcome Call color_mm1x7997.

The failure mode this system is prone to

A patient can end up in no queue at all, and nothing will report it. If a patient reaches a state that no rule accounts for — a Stage Advancer value nobody wrote a branch for, say — every filter skips them. No error, no warning, no red count.

This is why “nothing looks wrong” is not evidence that nothing is wrong, and why a patient who feels stuck is worth reporting even when you cannot point at anything specific.

05

What happens when you save

The main “Send to Monday” actions run a four-phase transaction. Knowing its shape tells you what a failure means.

Monday's API confirms a write before the value is searchable. If the app flipped the Stage Advancer immediately, the automation could fire and read the old values of the other columns — sending stale data to the next stage. The four phases exist to prevent exactly that.

The three toasts, and exactly what each one means

The message you get after a save is the single most useful piece of diagnostic information in the app. There are three, and they are not interchangeable:

What you sawWhat it meansWhat to do
“… — confirmed in Monday” Everything wrote and was read back successfully. The Stage Advancer was written last. Nothing. It is durable.
“Data in server — Monday confirmation still pending” The gateway has durably accepted the job and it will run. The app stopped waiting for Monday to confirm. Do not repeat the save. Repeating it writes twice. Check the board in a few minutes.
“Save failed — nothing was written” The transaction aborted. The Stage Advancer was not written, so the patient did not advance. Retry. If it fails again, report it — the item link and the time are what's needed.

Defined in src/lib/shared/verifiedWrite.ts. The pending case is GatewayPendingError; the panels that surface it are Chase Clinicals, Confirm Receipt, and the Doctor Appointments panel and dialog.

Worth knowing

Not every action in the app runs this four-phase transaction. The six main “Send to Monday” flows do. Some smaller inline actions — logging an attempt, marking complete, the escalation dialog, the Subscription save — write more directly and have less verification behind them. That difference is documented for engineers in the repository's write-reliability audit; operationally, it means a save that showed no toast at all is worth checking on the board.

06

Triage — symptom to owner

Find the symptom, do the one check, read the chip.

Family A — “Where is my patient?”

A patient disappeared from a rep's queue

Board data
Check
The Escalation column, then the controlling column for that stage (Gate 2 table).
If escalated
They are in a manager column. This is the designed behaviour, not a fault.
If snoozed
They return on the follow-up date. Note that Auth Outstanding and DVS ignore the status column entirely.

A patient is in no queue and in no count

App rules
Check
The Stage Advancer value. Is it one of the five exact strings listed under Gate 1?
Meaning
A value with no matching branch is skipped by every filter. Nothing reports it.
Fix
Either the value is wrong on the board (Board data), or the app is missing a branch (App rules). Report with the item link.

A patient is on the right board but in the wrong queue

Board data
Check
The splitter for that stage — Clinicals Method for Chase, Already In System for Profile Send Off.
Note
A blank Clinicals Method routes to Chase — Fax by design, so that nobody falls through.
Fix
Set the column on the board; the patient moves queues within a minute.

An escalated patient is not in any manager column

App rules
Check
Which escalation label the item carries, and which stage it is in.
Why it matters
Escalation removes a patient from the rep's list. If no manager chart also matches them, they are invisible everywhere.
Fix
Report it. This is the highest-priority class of bug in the system.

Family B — “I saved it and it didn't stick”

A rep says they saved it; the board is blank

The save
Check
Ask what the toast said (section 05), then read the item's Activity Log.
No write logged
It never reached Monday. Redo it and watch the toast.
Written, then changed
An automation or a bot overwrote it — that is Board setup or A bot, not the app.

It saved, but the patient never advanced

Board setup
Check
Whether the Stage Advancer actually changed on the item.
It didn't change
The save aborted at Phase 2 on purpose — see Figure 5. Retry.
It changed, nothing moved
The Monday automation is off, deleted, or erroring. A board admin checks it.

“Data in server — Monday confirmation still pending”

The save
Meaning
The job is durably queued on the server and will run. It is not lost.
Do
Wait, then check the board.
Do not
Do not redo the save. Repeating it writes twice.

One column reads blank for every patient

Board setup
Check
Whether that column was recently deleted and re-added on the board.
Meaning
Columns are matched by a hidden ID, not by their title. Deleting and recreating a column gives it a new ID; the app keeps asking for the old one and gets nothing, with no error.
Rule
Rename columns freely. Never delete and recreate one. A rename is safe; a recreate silently breaks reads.

A status label has a near-duplicate on the board

Board setup
Check
The label list for that column — look for two entries differing only in spacing or capitalization.
Meaning
Some writes match labels by exact text. If the text no longer matches, Monday creates a new label rather than failing.
Rule
Flag any status-label rename before it happens. Several rules compare exact strings such as Chase Clinicals and Parachute.

Family C — “The numbers don't agree”

A list and its own count disagree

The save
Check
Reload and wait a minute. Lists refresh every 30 seconds, counts every 60.
Meaning
A gap of up to a minute after any change is expected and not a fault.
If it persists
Then it is worth reporting as App rules.

A role bar and an Oversight chart disagree

App rules
Check
Whether the patients in the gap are escalated, and by how many the two differ.
Meaning
The same rule is written in several places and one copy has drifted. See section 07.
Report
Give every number you can see — bar, list, and chart. The pattern of disagreement identifies which copy drifted.

The burndown shows a role as “not connected”

App rules
Check
Whether it is a recently added role.
Meaning
The start-of-day snapshot has no entry for that role, so it shows “not connected” rather than a misleading zero. That is deliberate.
Fix
Code, in both snapshot generators.

Start-of-day numbers look wrong all day

App rules
Check
Whether the live counts look right. If only the comparison is off, it is the snapshot.
Meaning
The snapshot is taken once each weekday morning. If its rules drift from the live ones you get phantom in/out movement all day.
Fix
Code. It corrects itself the next morning once the underlying rule is fixed.

The FAX bar says “Done!” but faxes are in the inbox

Board data
Meaning
Once the unread count first reaches zero on a given day, the bar stays “Done!” until midnight Eastern, even as new faxes arrive.
Fix
Nothing — this is the defined behaviour. Work the Fax Inbox page directly rather than the bar.

Family D — “An outside system didn't do its job”

Eligibility results stay blank

A bot
Check
That Name, DOB, insurance and Member ID were filled in before the check ran. If they weren't, the run is aborted on purpose and the check never fires.
Timing
Results are polled every 4 seconds and revealed once they have been stable for 10 seconds. The whole run times out at 95 seconds.
Meaning
The app never writes eligibility results — a separate service does. A permanently blank field means that service did not write it.
Fix
Backend. Corrections are made through Profile Send Off; the Insurance board cannot run an eligibility check at all.

DVS or claims are not progressing

A bot
Check
The DVS and claims status columns on the item.
Meaning
DVS is automatic — that page is a read-only monitor. A failed or manual-review result escalates the patient by board automation.
Note
Supplies and pump claims are separate columns. A pump problem will not show in the supplies column.

A fax or email did not send

A bot
Check
The recipient address or fax number on the item, and that the person is signed in.
Meaning
Sending runs through a separate mail service and RingCentral, and does not touch Monday.
Note
Email recipients receive one grouped message; each fax number receives its own separate message.

Incoming calls stopped appearing on screen

A bot
Check
That person's own ring setting: all, list, or off.
Important
A narrowed setting silences that person's screen only. It can never make a call unanswerable by someone else.
If it's everyone
The call feed itself is down. There is a health check for exactly this — ask Josh.

Blank screen, or a page will not load

The save
Do
Reload the tab once.
Meaning
A tab left open across a new release loses the files it was going to load next. The app reloads itself once automatically when it detects this; a manual refresh does the same.
If a reload doesn't fix it
Then report it.
07

Why a fix sometimes half-works

This explains a specific, recurring pattern of confusion, and it is worth knowing even if you never open the code.

A queue rule is not written once. The same rule is repeated in five separate places, because five parts of the system answer five different questions — and three of them cannot share code with the others.

What this means for you in practice: when reporting a counting problem, name every place you saw it. “The bar says 12, the list shows 9, and the Oversight chart says 14” identifies which copy drifted. “The count is wrong” does not.

The rule files themselves carry this warning. See the header comments in src/lib/profile/referralSplit.ts and src/hooks/useRoleCounts.ts.

08

Where to look, and how to report

Four places, in the order you should reach for them.

ToolAnswersWho
The item's Activity Log
built into Monday		 Who changed which column, to what, and exactly when. The most useful diagnostic in the whole system, and it requires no special access. Anyone with board access
Pipeline Oversight
System Management → Oversight		 Where escalated patients went, and which manager column holds them. Every escalated patient is meant to land in one of these columns; one that lands in none is invisible app-wide. Managers
The gateway audit log Every request the app made — so you can establish whether a save was even attempted. Records metadata only; no patient data is stored there. Josh — it is key-protected
The health checks Whether the plumbing is alive. The gateway, the texting service and the incoming-call feed each have one. Josh

Reporting so it can be fixed the same day

The fastest reports answer the fork in section 03 before anyone has to ask:

Patient: [name + link to the Monday item] Stage/queue: [which page, chart or role bar] Expected: [what you thought would happen] Saw: [what actually happened] Toast: [exact wording, if there was one] When: [date + roughly what time] On the board: [what the relevant columns say right now] Also seen in: [any other count, list or chart that disagrees]

The last three lines save the most time. Toast distinguishes the three save outcomes in section 05. On the board settles whether it is a data problem or an app problem. Also seen in points straight at the section 07 mismatch.

Words you will hear

Stage Advancer
The one status column per board that Monday's automations watch. Changing it is what moves a patient to the next stage. The app writes it last, after confirming everything else landed.
Next Action Date
Controls the queue on the Medical Evaluation board. Blank, today or past all mean due now; only a future date hides the patient.
Follow Up / Follow Up Date
The snooze mechanism on the other boards. Which of the two actually controls the queue depends on the stage — see the Gate 2 table.
Escalation
Removes a patient from the rep's list and count, and puts them in a manager column. DVS is the exception and ignores it.
Propose Stuck
A rep's request that a patient leave the pipeline. It is a proposal only; a manager approves or returns it. It appears as “Final Escalation Required”.
Manager Intervention / Final Decisions
The two manager columns in Pipeline Oversight, corresponding to the two escalation labels.
Verified write
The four-phase save in section 05: snapshot, write, read back to confirm, then flip the Stage Advancer. If it cannot confirm, it aborts rather than advancing.
Gateway
The server the app talks to Monday through. It holds the credentials and logs every request, which is what makes an audit possible.
Baseline
The start-of-day count snapshot the burndown compares against, taken each weekday morning.
Stedi
The insurance eligibility check. A separate service runs it and writes the results to Monday; the app requests it and waits.
DVS
The automatic Medicaid verification stage. Bot-run; the page is a read-only monitor.
Parachute
An outside source for clinical documents. In the app, Email and Parachute share one queue.
Masheke / Samantha
Long-standing internal nicknames for the Medical Evaluation board and the Insurance board respectively. Same boards, older names.
