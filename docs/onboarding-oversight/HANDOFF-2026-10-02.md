## 1. The gateway, from zero

Before: the dashboard read monday's activity log, and every change made **in Command Center** showed up as one user,
the shared monday account (user id `100161122`, "Shared Command Center account"). You could see *that* the app did
something, never *who*.

What sits in between: in production every Command Center call to monday goes through a small server we run on
Railway, the **monday gateway** (`services/monday-gateway`, Railway service "cmd ctr server"). It adds the monday token
and records every write in its own Postgres table (`gql_log`), **including the signed-in person** (their
medicallymodern.com Google email) and which columns were written. Monday itself still only sees the shared account;
the gateway is where the name lives.

What we added to use it:
- **A read-only route on the gateway:** `GET /oversight/app-actors?since=<ISO time>` (`services/monday-gateway/appActors.mjs`
  and `appActorsRules.mjs`). It requires a verified Google sign-in and returns, for the four onboarding boards only:
  item id, board id, the person's email, the time, and the **column ids** written. It never returns a written value
  (the SQL selects only the JSON keys, so patient data never leaves Postgres). Caps: 60 days back, 100,000 rows (with
  a `truncated` flag), 60-second cache. For durable `/send` jobs it also returns when the job was queued (`startMs`),
  because those rows are logged when the job *finishes*, sometimes minutes after monday changed.
- **On the dashboard:** `src/lib/onboardingOversight/data/fetchAppActors.ts` calls it once per snapshot, and
  `src/lib/onboardingOversight/model/appAttribution.ts` (`attachAppActors`) matches each shared-account event to a
  gateway row: same item, same board, the event's column among the columns written, within
  `attributionMatchSeconds`, nearest first. It sets `actorKey` on the event in memory only, never in the IndexedDB
  cache. This is your spec's §3.10.1 **rule 2** ("Phase 7").
- **If the gateway can't be read** (not signed in, gateway down, fixture mode), events stay exactly as before and the
  header says "staff names unavailable".

**One more thing about the shared account.** It is not only Command Center. The intake web form, Stedi and the DVS
services write to monday with the same token directly, never through the gateway. Measured on Profile Send Off from
Sep 14 to Oct 2: 6,057 shared-account changes, only 56% of them Command Center writes. The rest (mostly the form,
around the clock) were being counted as staff touches. See commit `aa6ab66` below.

## 3. "Why escalated" (`7222d74`) in detail

- **Read live, never stored.** When a list opens, `fetchEscReasons` reads (read-only `gql`, 50 items per query) the
  stage's notes column for **that list's escalated rows only**, plus the Escalation Reason dropdown on MN and WC. The
  parsed reason lives in the list's React state, never on an `ItemRow` and never in the cache (CR-17).
- **Latest written reason wins:**
  - MN / INS / WC: `[Proposed Stuck · date · initials] reason`, `[Escalated to Final · …] why`, and on Insurance
    `[Auto-escalated · …] failed checks` (shown as "Benefits check failed").
  - Intake: the stamped `Proposed stuck: …` / `Escalated: …` lines, read through `intakeDecisionLine`, plus the stamp's
    time and initials (`escReason.intakeDecision`).
  - Nothing written: the MN/WC dropdown (`dropdown_mm2fhcd6`), then the automatic Edge Case trigger by name (attempts
    used up, evaluated 3+ times, Auth Denied group), else **"No reason written (likely a Monday automation)"**.
  - A return or approval written after the reason adds "written before a later return".
- **List summary strip:** counts by source (Proposed stuck, Escalated, Benefits check failed, …, No reason written);
  clicking one narrows the list. The search box also matches reason text.
- What the live boards showed when it was checked: MN's escalated patients sampled were all "Attempts = Escalate"
  with nothing written; most Insurance ones carry the Auto-escalated line; every intake one has a stamped line.
