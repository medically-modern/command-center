Role & Routing Spec

Every role: what puts a patient in the queue, what the rep must complete before the stage can advance, and exactly where each outcome sends them. Read from the code, not from prior docs.

Version 1.0 Issued 11 Aug 2026 Source commit b5a5f8f

00How to read this

Each role is one spec block with the same six fields. Entry is the predicate that puts a patient in the queue. Due is the snooze rule that decides whether they surface today. Gates are what must be filled before the primary action unlocks. Exits is the routing table — every outcome, the columns it writes, and the destination.

Three rules apply to every role

1 · The advancer is written last

Every "Send to Monday" runs executeWritesWithVerification: snapshot → write data columns → poll read-back (8 tries, ~12s) → only then write the stage advancer. If verification times out it throws and the advancer is never written. The patient stays put by design, because the automation would otherwise read stale siblings.

2 · Escalation removes a patient from the rep

An escalated patient leaves the role's list and its count and appears in a manager column. DVS is the only exception — it ignores escalation entirely. On the Medical Evaluation board, escalation index 2 (proposed stuck) is excluded from both the active and the escalated counts.

3 · Movement between boards is a Monday automation

The app only ever flips a status column. Board-to-board movement, item creation on the next board, and group moves are board automations. On the Medical Evaluation board this is not true of sub-stages: Sub-Stage color_mm1wyr92 is the advancer, so moving between Evaluate → Send Request → Confirm Receipt → Chase → Doctor Appointment needs no automation at all.

Destination legend

ADVANCES  moves to the next stage  ·  STAYS  remains in this queue, usually snoozed  ·  ESCALATES  leaves for a manager column  ·  TO A BOT  handed to an automated stage

Doctor Appointments

id doctorAppointments · /doctor-appointments · Sub-Stage Doctor Appointment (index 0)
Entry
Only via the Doctor Appointment Required dialog on a chase page. There is deliberately no way for a rep to set this on their own judgment. One rule is the entire state machine: Appointment Date set ⇒ a normal Chase patient snoozed to appt+1. Blank ⇒ this queue.
Due
Next Action Date rule. A patient whose Appointment Date is today-or-later is in Scheduled and nowhere else, whatever their NAD says.
Gates

A note is mandatory on every attempt (canLogAttempt). The attempt count is derived by parsing lines out of MN Workflow Notes — there are no per-attempt columns — so a note-less save would be indistinguishable from no attempt and hand the rep unlimited retries.

The 3-attempt cap is a rep guardrail only (apptCapApplies). An escalated patient has no limit; the manager working them logs as many as it takes.

Exits

Three ways out, and only three.

OutcomeWritesDestination
Patient booked an appointmentAppointment Date, Sub-Stage → 11, NAD = appt+1 (floored at today), Escalation → DoneADVANCES back to Chase
Third attempt spentEscalation → index 0, never index 2ESCALATES Manager Intervention
Won't schedule / wants to cancelPropose Stuck at any attempt — climbs the shared ladder, reason stamped with stage and attempt numberESCALATES one rung up
No answer · left messageAttempt line appended, NAD +1 business daySTAYS snoozed 1 business day
Spoke — patient will call the officeAttempt line appended, NAD +7 calendar daysSTAYS snoozed one week
Notes

The attempt line is the counter. Format is exactly 8/3/26, 1:38 PM · Phone call — No answer / no response · <note> —JH. apptAttemptsFromNotes matches {known method} — {known outcome} and numbers by position. A format change not mirrored in the parser does not error — it silently resets the count.

The count is read only from lines after the last reset marker (stage-entry stamp, or [Returned to queue). Without that, a patient re-entering the stage or handed back by a manager would arrive already capped.

Why a refusal doesn't wait for the third attempt: it's a rep judgment about what they were told, not a counter running out. It climbs one rung rather than jumping to Final so a manager reviews the refusal before the patient can leave the pipeline.

Entry clears escalation because the column is shared. Without it, a manager working an escalated chase patient who clicks the button delivers them into this queue already escalated — and escalated patients are hidden from this sidebar, so they'd be invisible on arrival with no error.

Sidebar sections differ by view, not access level: Awaiting reply and Scheduled render only when ?mv= is present (set by every Oversight column and nothing else). The manager view lists every patient in the stage including escalated ones.

06The shared escalation ladder

Cross-cutting. Submit Auth, DVS and Doctor Appointments all use the same stageActions.proposeStuckLevel.

ActionWhoEffect
Propose StuckRep or managerWrites one rung up from the patient's current label. An existing escalation, or a click from Manager Intervention, promotes to Final. Otherwise Submit Auth and DVS start at Manager; Benefits and Auth Outstanding go straight to Final. Reason stamped into the notes as [Proposed Stuck …].
Approve StuckManager, Final DecisionsMain Stage Advancer → Stuck, then clear the escalation — in that order.

Send back to managerFinal Decisions, DVS rows onlyFinal → Manager index 0. The only Final→Manager transition in the system; everything else raises or clears.
Manager resolveManager working the patientThe three Insurance stage pages pass managerResolve when ?manager=1. Completing the form clears the escalation and hands the patient back. Auto rules still run afterward, so a review that comes back denied re-escalates on the new facts.

The invariant that must not break

Every escalated patient must land in some manager chart. Escalation removes them from the rep's queue and the role count, so a state matching no chart is invisible in the entire app. Manager chart bars key on board facts while escalations are labels, so the two drift — which is why each Insurance manager chart carries a population rule wider than its bars. lib/oversight/insuranceCoverage.test.ts enumerates the reachable (stage × escalation) states and fails if one goes blind.

There is no Escalate toggle in the Insurance UI and one must not be reintroduced. components/samantha/EscalateButton.tsx was deleted. A send writes the Escalation column only when an auto rule decides one; an auto rule only ever raises. The previous "manual toggle is the floor" rule read p.escalated, which is hydrated from the board, and re-wrote it on every send — silently promoting pending proposals past review, and silently clearing flags raised since the last poll.

Board-side rules the app depends on

  • Rename columns freely; never delete and recreate one. Column IDs are the contract. A rename keeps the ID and reads keep working; a recreate assigns a new ID and reads return empty silently.
  • Status label text is load-bearing in specific places. Sub-Stage matching, the Evaluate "Option A" dropdowns, and Clinicals Method all compare exact strings. Prefer index writes; where a label is compared, a casing change makes Monday create a duplicate label rather than fail.
  • A status write by index is silent if the index has no label. Verify settings_str before adding an index — this is why Doctor Appointment is index 0 and not 12.
  • Never route a machine-parsed date through a text column across boards. Monday's create-item automations type-sniff TEXT tokens: 2022-01-01 is re-rendered as 01 January 2022. Dates ride in DATE columns, which copy verbatim.
  • Monday dates are timezone-naive ET. Compare in ET, never with a bare new Date() in a UTC runtime — which is what Railway and CI are.
